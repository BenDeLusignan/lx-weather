# LX Weather: vision

This is the single source of truth for what we're building and the rules we build by.
Read it before you plan, build or review anything in this repo.

## How to read it

Every rule here is labelled with who owns it, because that decides who you talk to about it:

- **Ben's decisions.** Ben made these calls. Follow them. If a request conflicts with one, raise it with Ben. Don't quietly deviate.
- **Team conventions.** The way the team builds. Follow them too, but they aren't Ben's calls: the team can change one through review (raise it with your teammate, not Ben), and updates this doc in the same change.
- **Current state** describes the code as it is today, not a target.
- **Open questions** and **Proposals awaiting Ben** are not decided. Don't build on them as if they were, and don't settle them yourself.

## What and why (Ben's decision)

A weather app for tennis players in Northern Ireland, where the weather is very unpredictable. It takes the forecasts of the top five European weather providers (Ben's examples: Apple Weather, Met Office, BBC Weather), combines them into one aggregate forecast, and shows it for each of the top tennis clubs in the country, so a player can see whether they'll actually get to play.

Ben's words: "this one will actually be incredibly useful". It is a portfolio project, built under the LX Studios name (hence `lx-weather`).

## Who it's for (Ben's decision)

- **Tennis players in Northern Ireland**, Ben and his friends first.
- **Users sign up and pick their club from the list.** That club is their home club, and its location is their home location. The app never checks their real location (no GPS).
- Used on a phone as much as on a computer.

## Platform (Ben's decision)

A website / web app that works on **both the computer and the phone**.

## Core flow (Ben's decisions)

1. **The landing page is the log in** (Ben: "Landing page is a log in"). Team's reading, not Ben's words: a new user reaches sign-up from it (Ben earlier: "Users will sign up and select their club from the list").
2. **Once logged in, the home screen is the user's home club's weather, with the club name at the top**, for **one week** (Ben: "Let's just do one week then"; this replaces the first brief's current week and next week).
3. **Every day shows its times from 10:00 to 22:00, and each block gets a traffic-light score** (Ben's earlier words: "show the times for each day from 08:00 to 20:00 and have a score for each block"; on 11 Oct 2026 Ben changed the window: "change the time window and go from 8-19 change to 10-21", meaning blocks starting 10:00 to 21:00, so 10:00 to 22:00. The 08:00 to 20:00 window is superseded):
   - **Green:** a good chance of no rain or wind.
   - **Yellow:** passable level of play.
   - **Red:** very unlikely you will get to play.

   **Every hour box is the same size, and shows the rain chance and the wind speed** (Ben: "make sure every box is the same size. Have the rain percentage and the wind speed in each box"; also "boxes do not need to list x out of 5 based on how many sources they have"). *Why:* rain and wind both decide the light, so a box that said 3% rain but was red because of the wind would confuse people (Ben: "Rain and wind are needed as some say 3% as in chance of rain but are red because of the wind which may confuse users"). So the box never shows "N of 5 providers"; the count is still shown in the detail that opens from the box (Team convention 1).

   Team's readings, not Ben's words, so say if any is wrong: **one week is today and the next six days** (not Monday to Sunday); **a block is one hour** (10:00 to 11:00, then on to 21:00 to 22:00: twelve a day); **the score is the green/yellow/red light**; the blocks of today that are already over are not shown; all times are UK time (Europe/London); **the box shows the wind in mph** (it is small), and the detail shows mph and km/h.
4. **An Away Game button** on the home screen shows **a list of the other clubs, alphabetically**. Clicking one shows **the same screen as the home screen, with that club and its data** instead (Ben: "once they are clicked you see the same screen as your homescreen but with the selected club and its data instead").
5. **There is always a button at the top of the screen that takes the user home, with an Account button** for changing the home club "if that ever happens" (Ben: "There should always be a home button at the top of the screen with an account button for changing your home club if that ever happens"). On 11 Oct 2026 Ben renamed the home button: "change the home button to say LX Tennis Weather, it will still bring the user to the home screen". So it reads **LX Tennis Weather** (beside the brand mark) and still goes to `/`. Later the same day Ben added a control to that header: "make dark mode/light mode a slider the user can choose from the header", so the header also carries **a light/dark slider**, between the name and Account (see Theme).
6. **Aggregated figures, with the sources one tap away.** Temperature, wind, rain and the rest are shown as an **aggregate** of the five providers. An **expand source data** control shows what each of the five providers says specifically.
7. **No day icon** (Ben: "No day icon as it could rain 80% of the day but not the 20% you actually want to play at"). Only the hour blocks are scored; nothing sums a day into one light.

8. **The user chooses which days and times they see** (Ben, 11 Oct 2026: "also in the account settings the user can select what days and what time frames they actually want to see on their account"; the light and dark mode were in the same message, see Theme).    - **Time frames** are the twelve one-hour blocks of Core flow 3 (10:00 to 21:00), each on or off, not a free range.
   - The choice applies to the home club's week and to every away club's week, and is kept per account.

## Product rules

### Ben's decisions

1. **The headline is the aggregate; the providers are the detail.** The default view never makes the user read five forecasts. The five are available under "expand source data" (Core flow, 6).
2. **Never invent weather.** If a provider has no data or can't be reached, say so and show what the others say. No placeholder or sample numbers dressed up as a forecast. If nothing can be shown, show an honest empty state.
3. **The traffic light follows the chance of rain and the wind.**
   - **Rain** (Ben: "Rain is what people are most worried about"):
     - **Red:** over 70% chance of rain.
     - **Yellow:** 31% to 70%.
     - **Green:** 30% and under (Ben: "Let's have rain percentage as 30 and under being classed as good"; it was under 40% before).
   - **Wind:** Ben: "strong wind definitely makes the game unplayable, but I can't remember what speed feels too much". So a strong enough wind is red; the speeds are the team's pick (Team convention 4), for Ben to confirm.
   - **A block's light is the worse of its rain light and its wind light.**

   Team's reading, not Ben's words: exactly 70% is yellow (Ben changed only the green limit, so the red limit stays at over 70%), and the light follows the whole-number % shown on screen (30.4% shows as 30% and is green; 30.5% shows as 31% and is yellow; 70.4% shows as 70% and is yellow; 70.5% shows as 71% and is red), so the number and the colour never disagree.
4. **Units:** temperature in **Celsius**; wind in **mph and km/h**. Team's reading, not Ben's words: both wind units are shown together wherever wind appears (the way LX Tennis shows lb and kg), so nobody has to pick; the one exception is the small hour box, which shows mph only (Core flow 3).
5. **The five providers are the five whose data is most publicly accessible** (Ben: "I'm not sure who they are, but I'm thinking this app will replace a player having to open the 5 most popular weather apps and making an average decision themselves, so whoever has the 5 most publicly accessible data"). Which five is the team's call, below.
6. **Combining the forecasts:** whichever method gives the most reliable end point (Ben: "Whichever would work best"). The team's pick is below.
7. **Same stack as the other LX projects** (Ben: "Use what we have been using so far"): Next.js (App Router) + TypeScript, CSS Modules (no Tailwind), SQLite through Drizzle (a local file in development, Turso once hosted), hosted on Vercel. The details are in the LX Tennis vision. The look and theme are not part of this decision (see Open questions).
8. **No charging, no ads** (Ben, 11 Oct 2026: "I wasn't planning on charging people for this or running ads"). This is why Open-Meteo's free non-commercial tier applies (Team convention 2).

### Team conventions

1. **Every figure shows how many providers it's built from** (e.g. "4 of 5 providers") when fewer than five contributed, so an aggregate from two sources is never mistaken for one from five. **Exception, Ben's decision: the hour boxes in the week strip don't show it** (Core flow 3); the detail that opens from a box does.
2. **The five providers are Met Office (UKMO), ECMWF, DWD ICON, NOAA GFS and Environment Canada GEM, all fetched through [Open-Meteo](https://open-meteo.com)** (the team's pick, measured on 11 Oct 2026 for a Belfast location). *Why:* Open-Meteo is free for non-commercial use, needs no key, and serves all five from one call per location. Ben's decision 8 (no charging, no ads) keeps the site non-commercial, so the free tier applies; **a commercial plan is needed only if that decision changes** (the site starts charging or showing ads). Open-Meteo's terms can change and it can block misuse, so don't assume the free tier is permanent. The free limits are 10,000 calls a day and 300,000 a month. Open-Meteo's data is CC BY 4.0, so **Open-Meteo is credited on the site, with a link**; it lists the Met Office data as CC BY-SA 4.0, so **the UK Met Office is credited too, with that licence linked** (see Open questions for what ShareAlike may mean for us).
   - **These are forecast models, not the consumer apps.** The apps (Apple Weather, BBC Weather and the rest) post-process models like these, and none has a free public data feed. So the app replaces opening the apps by combining the models underneath them.
   - **Why not the apps Ben named.** BBC Weather has no public API (its only developer feed is a 3-day, non-commercial RSS feed documented in 2011). Ben has dropped Apple Weather ("ignore apple weather then"; it needs a paid Apple Developer membership) and the Met Office's own feed ("just pull the data from API": the Met Office model through Open-Meteo is the Met Office source).
   - **Why not MET Norway or Météo-France.** Both are free, but neither gives a chance of rain, only an amount, and the traffic light needs the chance (Ben's decision 3).
   - **How far ahead each one reaches** (when the chance of rain is last given, and when everything else is, for 11 Oct 2026):

     | Provider | Chance of rain to | Everything else to |
     | --- | --- | --- |
     | Met Office (UKMO) | 20 Oct | 17 Oct |
     | ECMWF | 25 Oct | 26 Oct |
     | DWD ICON | 16 Oct | 18 Oct |
     | NOAA GFS | 26 Oct | 26 Oct |
     | Environment Canada GEM | 26 Oct | 21 Oct |

   - **Consequence:** for a week starting 11 Oct every figure has four or five providers (16 Oct: DWD ICON's chance of rain has ended; 17 Oct: the Met Office model's other figures end at 13:00). Convention 1 shows the count in the hour's detail, so it is never hidden. Outside the first week there are fewer, which is a reason to keep it to one week.
3. **Rain chance is the mean of the providers that give one; temperature and wind are the median.** *Why:* each provider's chance is already a probability, so their mean is a probability too and every provider counts; the median keeps one model with a wild temperature or wind from dragging the figure. **Backtested 11 Oct 2026** (`scripts/backtest/`, results in `scripts/backtest/results/summary.txt`) against hourly airport observations (Belfast City, Belfast International, City of Derry; 11,553 station-hours, 340 days, Aug 2025 to Oct 2026), forecasts 1 to 6 days ahead from Open-Meteo's Previous Runs API:
   - **The blend beats every single provider** at every lead, including the Met Office alone: wind error 0.3 to 0.8 mph lower, and the light matches the observed light 4 to 6 points more often. Every Met Office-first schedule tried (hard switches for the first 1 to 4 days, tapers) was also worse, so the app keeps the equal blend. Met Office wind at 5 and 6 days is no better than a constant guess.
   - **Dropping the Met Office from the blend costs almost nothing** at 2 to 6 days and a little at 1 day (wind error +0.11 mph).
   - **Limits:** the rain chance the app shows (ensemble-derived) is not stored for past days, so rain at 1 to 6 days was tested through a calibrated proxy from precipitation amounts; the real chances were checked only a few hours ahead (all five only for 19 days). Rain is judged from airport weather reports (occurrence, not amount). Only three airfield stations: nothing within 45 km of Enniskillen, Omagh or Newcastle, and no club west or south is validated. Gusts and temperature untested. To test the real rain chance, log the live forecasts for 6 to 8 weeks and compare.
4. **Wind lights, by sustained wind speed** (Ben didn't give speeds; these are the team's pick, to be confirmed): **green under 10 mph, yellow 10 to 15 mph, red over 15 mph**, on the whole-number mph shown, like the rain light. *Why:* one tennis-conditions guide (Playable) says wind noticeably affects play from about 7 mph and is "genuinely unplayable for most recreational players above 15 mph sustained". Northern Ireland is windy, so the team put yellow at 10 rather than 7, so a normal breeze isn't a red day. The speed is the forecast's wind at 10 m up in the open, and courts are often sheltered; gusts, which the same guide says matter as much, are not used yet (see Open questions).
5. **Forecasts are fetched on the server and cached** for up to an hour per forecast point, so the five providers aren't called on every page view and the site stays far under Open-Meteo's free limits (10,000 calls a day; 18 clubs at one call an hour is 432). One hour is the team's pick; the models update a few times a day. Provider keys, if any are ever added, stay on the server.
6. **Accounts follow LX Tennis's approach, and are checked on the server.** Email and password; **the password rule is Ben's decision** (11 Oct 2026: "maybe we should make the password requirement min 12 characters with at least one number, one capital, and one symbol"; he also asked for a live checklist in the form, which is only a helper for the rule below): a password of at least 12 and at most 1024 characters with at least one number, one capital letter and one symbol, defined once in `src/forms/password-rules.ts` and enforced on the server by `passwordMeetsRules`. It supersedes the earlier "at least 12 characters" (the team's own pick, from LX Tennis). The terms are the team's reading, not Ben's words, so say if any is wrong: a number is a decimal digit (0-9); a capital is any uppercase letter (Unicode, so "É" counts); a symbol is any character that is not a letter, a combining mark, a digit or whitespace (so `#`, `!`, `_`, `-` and emoji count; a space or a decomposed accent does not). The rule applies only when a password is set, at sign-up and for the new password in Change password; it is never applied at log in or to the current-password field, so an account made under the old rule keeps working with whatever password it has. **The live checklist** under the field (Ben's ask; the details are the team's reading, not Ben's words, so say if any is wrong) lists the four rules, in the order and words of `PASSWORD_RULES`, and ticks each one the moment it is met and un-ticks it if the character is deleted, using the very functions the server uses. It is only a helper: it never blocks the submit and the server decides, so the input has no browser `minLength` (the browser's own "lengthen this text" bubble would speak before the checklist and the server's message; `maxLength` stays, it only stops typing past the cap). A row is an empty ring when not met and a ticked disc when met, with "met" or "not met" in text for screen readers, so colour is never the only signal; one short polite spoken line names the rules that changed, and nothing is spoken when no rule changes. Passwords hashed with scrypt; a signed, HttpOnly, SameSite=Lax cookie session (Secure in production) from `SESSION_SECRET`; failed log ins and refused sign-ups counted per email and per client address in the database, with short lockouts (a minute, then five, then fifteen). A wrong password and an unknown email get the same message. `getCurrentUser()` (`src/auth/current-user.ts`) is the boundary: every screen with account data and every Server Action calls it and refuses when it returns null; `src/proxy.ts` only does the quick cookie check so a logged-out visit to `/away` or `/account` gets a real redirect. Forms work before JavaScript loads (plain POST to a Server Action that always ends in `redirect()`), and report errors as a flag in the URL, never what the user typed. *Why:* same reasons as on LX Tennis; anyone can call a Server Action directly, whatever the page shows.
   - **Changing the password** (Ben, 11 Oct 2026: "account needs the option to change password"; everything below is the team's reading, not Ben's words, so say if any is wrong). It is a form on the Account page (`changePassword` in `src/auth/actions.ts`, logic in `submitPasswordChange` in `src/auth/submit.ts`) that calls `getCurrentUser()` and sends a visitor to `/`. Checks, in this order: every field is a string within bounds; the new password meets the password rule (as at sign-up, which also caps it at 1024 characters; the current password is never rule-checked, so an account that predates the rule can still change its password); it equals its confirmation; it differs from the current one; then the current password is checked with scrypt against the stored hash. The first four only compare what was typed, so they cost no attempt; a wrong current password is counted by the same limiter and lockouts as a wrong log in (per user id and client address, plus the address counter shared with log in and sign-up, keys hashed with `SESSION_SECRET` so no email or address is stored), so a stolen session can only guess slowly (a thief who changes address gets a fresh per-account allowance each time and is held only by the shared per-address cap, as at log in). A refused attempt never reaches scrypt while locked, and a limiter that can't be written refuses (fails closed). A successful change clears the counter like a log in does. The write is one conditional update, only if the stored hash is still the one that was checked (`changePasswordHash`), so two changes racing can't both succeed; the loser writes nothing and is told. *Other devices:* a session carries a fingerprint of the password hash, so the change logs out every other device at once; this device gets a fresh session in the same action and stays logged in. The refusals say only what the user typed was wrong; the URL never carries a password. No table change was needed.

### Team conventions

1. **Colours only via the semantic tokens** in `src/app/globals.css` (`--color-*`, `--light-*`). No raw hex or `rgb()` in components or CSS Modules. There is one layer of tokens, and each theme-dependent token is written **once** as `light-dark(light value, dark value)`, so the two values sit side by side and cannot drift; the only tokens that are the same in both themes are the mark's colours, `--color-mark-bg-top`, `--color-mark-bg`, `--color-mark-rays` and `--color-mark-ball`, which are plain values (`--color-mark-edge` is none by default and the header sets it per theme), and `--theme-is-dark`, which is 1 when the dark theme is in effect, set from the same two conditions as `color-scheme`, because the switch's knob slides to a position and `light-dark()` takes only colours (the header is light blue in the light theme and black in the dark theme, so `--color-header-*` are `light-dark()` tokens: Convention 10). *Why `light-dark()`:* the theme can come from two places (the device, or the user's choice with the header's slider), and writing the dark values twice, once for each, is the usual way to get a drifting copy. The theme is chosen by the `data-theme` attribute on `<html>` (`light` or `dark`; **no attribute means follow the device**), which sets `color-scheme`, which is what `light-dark()` reads. *Trade-off:* `light-dark()` needs Chrome 123, Safari 17.5 or Firefox 120 (2024) or newer; on an older browser the colours would not apply. Use the tokens, not a `@media (prefers-color-scheme)` rule, in components. Also use the other tokens where one exists: `--font-size-*`, `--space-*`, `--radius*` (`--radius-sm` for cells, `--radius` for cards, inputs and buttons), `--content-width`, `--narrow-width`, `--touch-target`, `--focus-ring-width`, `--duration-fast`. The two places that can't read CSS variables, `src/app/icon.svg` and the `viewport` theme colours in `src/app/layout.tsx`, mirror tokens (convention 5).
2. **Contrast: WCAG AA in both themes.** Text and its tokens are at least 4.5:1 on the surfaces they sit on (in the dark theme that includes the second grey, `--color-surface-sunken`, which the link and the muted text also sit on at hover; in the light theme, the light blue-grey card and its darker hover step); icons and the edges of controls are at least 3:1. The measured ratios are in the header comment of `globals.css`, with the header's text, hover and focus ring; a new colour token needs its ratio checked and recorded there, and the red lights must stay clearly apart from the accent blue (a different hue as well as a different shape and word). Known exceptions, all recorded there: in the light theme the amber passable triangle is light by nature (2.1:1 on its cell) so it is outlined in the dark text colour (8.9:1) and its shape never depends on the fill; the light theme's amber warning edge on a Notice (2.2:1) only tints the edge, the words and the card's own border carry the meaning; and the mark's tile on the light theme's blue header (2.2) is decorative (the words beside it are the name), with a hairline ring in the header's navy added there (the dark theme's tile is 4.5 on black, so none). The mark's rays and ball on the tile, and the slider's edge, knob and icons, are at least 3:1 (measured in `globals.css`).
3. **A light is never shown by colour alone.** Always the shape (`LightIcon`) and the word (`lightWord` in `src/weather/format.ts`) with it; use `LightBadge` for a light on its own. Never add a day-level light (Ben's decision, Core flow 7).
4. **Breakpoints.** CSS custom properties can't be used in `@media`, so the scale is written down here. Styles are mobile-first (`min-width`). The site uses one:

   | Breakpoint | Used for |
   | --- | --- |
   | `48rem` (768px) | wider page gutters (`layout.module.css`, `site-header.module.css`, which also puts the wordmark on one line instead of stacked and gives the header's links more padding); the club name and its button share a row (`club-weather.module.css`); the day strip goes from two balanced rows (6 + 6 with all twelve hours; 4 + 3 with seven) to one row of one column per chosen hour (twelve with all of them) (`day-strip.module.css`, and the same columns in `loading.module.css`); the hour card gets more padding and its three figures sit side by side (`hour-cell.module.css`, `block-detail.module.css`); the room kept under the last day for its open hour card is smaller (`day-strip.module.css`); the log in and sign up card gets more padding (`auth-card.module.css`) |

The Away list is one alphabetical column at every width, held to `--narrow-width` (Ben, 11 Oct 2026: "make the list of clubs in alphabetical order one list, I don't like the three columns"). `stripColumns` and `gridColumns` in `format.ts` decide the column counts and places that the strip sets as `--columns-phone`, `--columns-wide` and `--col-*` (on a phone `HOURS_PER_PHONE_ROW`, 6, hours or fewer are one row, more are two rows of `ceil(n / 2)`); the 6 fallbacks in `day-strip.module.css` and `loading.module.css` are only for a missing variable. - `/account`: email, home club (a select, validated on the server against the club list), then two settings, each its own form that works with no JavaScript and is checked on the server: Days you see (Monday to Sunday checkboxes) and Times you see (twelve checkboxes, 10:00 to 21:00); the light or dark choice is no longer here, it is the header's slider; a save comes back to the page with a confirmation, a refusal (nothing chosen, an unknown value) with a message and nothing changed. Then Log out (which returns to `/`).
- `/account` also has Change password, its own small form like the others (works with no JavaScript, checked on the server): current password, new password (meeting the same password rule as at sign-up, with the same live checklist under the field) and confirm new password, with its own Save button. A change comes back to the page with "Password changed. Other devices have been logged out."; a refusal (a field missing or too long, a new password that doesn't meet the password rule, doesn't match its confirmation or is the same as the current one, a wrong current password, or too many wrong guesses) comes back with a message and nothing changed. The page and the behaviour are the team's reading of Ben's request, not Ben's words (Team convention 6).
- Logged-out visits to `/away*` and `/account` go to `/`. Every logged-in screen has a header with the LX Tennis Weather link (the brand mark and the name, to `/`), the light/dark slider and Account; the home screen has an Away Game button. If a stored home club id is no longer in the club list, the user is sent to `/account` to choose again.

**How it works**

- The week screen is `ClubWeather` (`src/components/club-weather.tsx`), used by both `/` and `/away/[clubId]`: an "Your home club" or "Away game" label, the club name as the h1 (Belfast also lists the five clubs it stands for), the Away Game button (home screen) or a link back to the list (away screen), then a line saying the colour is decided by the chance of rain and the wind speed, then the week, then, last of all, the credit ("Weather data by Open-Meteo.com (CC BY 4.0), including UK Met Office model data (CC BY-SA 4.0)", each licence name linked, Team convention 2). The credit is the very bottom of the page (Ben, 11 Oct 2026); the last day keeps room under it while an hour card is open, so the card can't cover it (`day-strip.module.css`). The week (`club-week.tsx`, `day-strip.tsx`, `hour-cell.tsx`, `block-detail.tsx`, `source-table.tsx`) is seven day headings, each with a strip of one cell per hour showing the hour, the light as a shape and a word (Good, Passable, Unlikely, or Unknown), the chance of rain and the wind in mph, each in whole numbers on its own line (a dash where there is no data). The cell is a fixed size, never shows "n of 5", and has screen-reader text for both figures. A tap opens that hour's card: the light with its reason when unknown, temperature, chance of rain and wind in mph and km/h each with "n of 5 providers" when fewer than five contributed (rain and wind also show the light they give), and a native `<details>` "Expand source data" with the five providers' own figures (a gap says "no data"). A provider with nothing at all is named above the week. If the fetch fails, or all five providers are unavailable, the screen says the forecast can't be loaded right now and shows no numbers. Until the forecast arrives the week is grey placeholder cells of the same height (`components/loading.tsx`). The hour cells are native `<details name="hour">`, so they work before JavaScript has loaded and opening one closes the last.
- `fetchHourlyForecast` makes one Open-Meteo call per club for the five providers; `src/weather/forecast-cache.ts` caches that fetched forecast per club (`"use cache"`, never served past an hour; Belfast's five clubs share its one entry). A failed fetch is not cached. `buildWeek` runs per request with the current time, so finished blocks drop out even from a cached forecast.
- `buildWeek` turns the forecast into seven UK days (today plus six) of 10:00-22:00 hour blocks (blocks starting 10:00 to 21:00), each with the aggregate temperature, rain chance and wind (Team convention 3), how many providers each is built from, every provider's own value, the rain light, the wind light and the block's light (the worse of the two; unknown unless both are known or one is red). Which hourly values feed a block is explained in `blocks.ts`. A provider with no value is a gap (`null`), never filled; a block with no data is still returned with `null` figures and a `null` light.
- **The user's days and hours** are applied in one place, `filterWeek` (`src/preferences/week-view.ts`), which `ClubWeek` runs on what `buildWeek` returns, for the home and every away club alike. `buildWeek` stays a pure function of the forecast and the clock and the same week serves everyone. A day that is off is dropped, a block outside the chosen hours is dropped, and a chosen day with none left stays, with no blocks, so the screen says so; nothing is invented. A day keeps its place in the week (so Today and Tomorrow still name the right days) and the chosen hours stay in order.
- **Settings are stored on the `user` row** as `theme` (`system`, `light` or `dark`), `days` and `hours` (a bitmask each: Monday is bit 0 and the 10:00 block is bit 0), added by an additive migration whose defaults (`system`, all days, all hours) mean an account made before them reads as it always did. Table CHECKs refuse an empty or out-of-range set; the same rules live in `src/preferences/preferences.ts` (pure, unit-tested), which every Server Action (`src/preferences/actions.ts`, each checking `getCurrentUser()`) and `updatePreferences` apply, and a stored value that can't be right reads as the default rather than hiding the week.
- **The theme reaches `<html data-theme>` through a cookie and a tiny inline script** (`src/preferences/theme.ts`), chosen over the usual alternatives: the root layout's shell is static (Team convention 9 and the Suspense in `layout.tsx`), and reading the user or a cookie in the layout would make every page wait for it; a script in `<head>` that copies a cookie onto `<html>` runs while the HTML is parsed, before the first paint, so there is no flash of the wrong theme. The cookie `lx_weather_theme` holds only `light` or `dark` (`system` has no cookie, so no attribute, so the device decides), is not HttpOnly because that script reads it, SameSite=Lax, a year, and no personal data. It is set when the theme is saved and when someone logs in or signs up (so it matches the account on that device) and it is kept after log out, so the log in and sign up pages follow the last choice on that device. The database is the record; `ThemeSync` (a small client component behind Suspense in the layout) puts the account's choice on `<html>` and the cookie once the page knows it: right after a save (a save is a navigation inside the page, which doesn't re-run the script) and on a device whose cookie is stale because the choice was changed on another. **Trade-offs:** the server's HTML carries the script, not the attribute (the browser sets it before painting); with JavaScript off the theme can't be applied and the site follows the device (the forms still work); the browser-bar colour (`themeColor`) follows the device, not the choice, because it is static metadata.
- **The header's slider** (`ThemeSwitch`, `src/components/theme-switch.tsx`) is one control built as a form of two stacked submit buttons, `theme=dark` ("Switch to dark mode") and `theme=light` ("Switch to light mode"), posting `saveTheme` (`src/preferences/actions.ts`), which checks `getCurrentUser()`, saves through `submitTheme`, refreshes the cookie and redirects back to the page the slider was used on. *Why two buttons with one shown, and not one toggle:* an account on "match my device" has no server-side answer to "which way is the other way" (the server can't see the device's setting), whereas "make it dark" always has one, with or without JavaScript. So the page's own CSS decides, from the same two conditions as `--theme-is-dark` (`<html data-theme>`, or with none the device's `prefers-color-scheme`): only the button for the theme not in effect is displayed, the other is `display: none`, so there is exactly one button to see, tab to or hear, named for what it does, right on first paint, before the scripts load, and with no flash. *Why not one client component that reads the theme and sets a hidden value:* it would need JavaScript to be right for "match my device" and its label would have to be kept in step by script. The one thing CSS can't do is keep keyboard focus when the shown button swaps, so `ThemeSync` hands it to the new one (Team convention 9). The switch is one picture, a single track and knob behind the transparent buttons, so the knob still slides. *Why it goes back to the page:* the slider lives in the root layout, which doesn't know the page, so the action reads the `Referer` (`src/preferences/return-path.ts`: same-site only, the path without its query so an old "saved" message isn't replayed, anything odd goes to `/`). *Where the knob is* comes from CSS, not the server: `--theme-is-dark` (set from `<html data-theme>` or, with none, the device's `prefers-color-scheme`) slides it, and the sun and moon swap colours with `light-dark()`, so it is right on first paint and for "match my device", with no flash. **Known limits:** the control is 80px wide by 44px tall, so it is not square but the whole of it is the touch target; with the app's scripts blocked the switch still posts and the next page carries the new theme through the cookie (checked 11 Oct 2026 by blocking the scripts), and with JavaScript off altogether the header never appears in development (the known gap in Team convention 9).
- Nothing is rounded in the engine; the screen rounds at display (whole % and mph and km/h, one decimal for °C), and the lights follow the whole numbers. A provider that doesn't reach that far ahead is a `null` in a block's per-provider values, which looks the same as an outage; only a provider with nothing at all is in `unavailable`. If all five are unavailable the fetch still returns normally, so the screen checks for that as well as for `ForecastFetchError`.
- There is no day icon (Ben's decision, Core flow 7).
- Two tables: `user` (email, password hash, home club id, created at, and the user's theme, days and hours) and `login_attempt` (the limiter's counters, keyed by a hash, so no email or address is stored). The home club id is a text column checked against `CLUBS` in code at every write, not a foreign key.
- **Hosted** on Vercel (https://lx-weather.vercel.app) with a free Turso database in AWS eu-west-1 (Ireland), so the production database is not a file. The environment variables and how migrations are run are in the README, "Deploying". Before they were set (11 Oct 2026) the pages loaded but every sign-up crashed, most likely because `SESSION_SECRET` was missing (inferred from the code; the server logs were not read).
- **Not built:** password reset, email verification. Without email verification, a refused sign-up can still be read as "that email has an account"; the limiter slows probing but doesn't stop it. A password can be changed only by someone who knows the current one (Team convention 6), so a forgotten password still can't be recovered.

**Run it:** see the README (`npm install`, copy `.env.example` to `.env.local` and set `SESSION_SECRET`, `npm run db:migrate`, `npm run dev`). `npm run forecast -- <club id>` (or `<latitude> <longitude>`) prints the week live; `npm test` runs the tests.
